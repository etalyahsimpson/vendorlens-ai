# ML Methodology

This document records exactly how the VendorLens AI matching model is built,
trained, evaluated and qualified. Every number in `reports/metrics.json` and
`reports/model_evaluation.md` is produced by the code described here — nothing
is hand-entered or copied from examples.

## 1. Dataset provenance (synthetic, seeded, fully disclosed)

All supplier records are **fictional**, generated by
`backend/vendorlens/data/generator.py` with a fixed seed (**42**):

- **850 records across 292 canonical supplier entities** (240 base companies,
  40 hard-negative "lookalike sibling" companies, 12 namesake companies).
- Each canonical entity contributes **2–4 records**: a base record plus 1–3
  aliases with realistic corruption — legal-suffix changes (`LLC` ↔ `Inc.` ↔
  none), casing (`WEXFORD GLASS`), spacing/punctuation, single-character
  typos, dropped words, legacy domains (`…-group.example`), missing websites
  (~10%), moved addresses, and stale postal codes.
- **Hard negatives** are distinct companies that share a name prefix, city and
  postal prefix with a real entity but differ in the core business word and
  website (e.g. *Pemberly Electronics Industries* vs *Pemberly Print
  Industries*). **Namesakes** are identical names belonging to companies in
  different regions. These make the task non-trivial and teach the model that
  similar names are not automatically the same business.
- Websites use the reserved `.example` TLD. City/state pairs are real US
  locations; street numbers and postal suffixes are fictional.
- The generator is deterministic: regenerating with seed 42 produces
  byte-identical CSVs (asserted by `tests/test_generator.py`).
- The **ground-truth `canonical_entity_id` labels exist only in the labeled
  pipeline file** (`data/generated/suppliers_labeled.csv`). They are never
  present in the bundled sample CSV, in API responses, or in the inference
  feature path.

**External validity.** The benchmark measures behaviour on *representative
generated corruption patterns*, not on real procurement data. Results are
evidence of a correctly functioning pipeline and honest baseline comparison —
they are **not estimates of production accuracy**. This qualification also
appears verbatim in `reports/metrics.json` and on the model-evidence screen.

## 2. Normalization

`backend/vendorlens/ml/normalization.py` (shared by training and serving):

- Names: NFKD → ASCII fold → lowercase → punctuation → whitespace collapse →
  legal-suffix token removal (`llc`, `inc`, `ltd`, `corp`, `gmbh`, …).
  Suffix stripping is a **feature transformation**, never evidence of legal
  identity; the suffix pair is compared separately as explicit features.
- Websites: scheme/`www.`/path stripping to a bare comparable domain, so
  `https://www.acme.example/about` equals `acme.example`.
- Addresses: lowercase, punctuation, street-type abbreviation map
  (`Street→st`, `Suite→ste`, …).
- City/state/postal: case folding, whitespace removal where appropriate.
- Original values are always preserved for display and export.

## 3. Candidate generation (FAISS + deterministic blocking)

Brute-force all-pairs comparison is avoided:

1. `TfidfVectorizer(analyzer="char_wb", ngram_range=(2,4))` over normalized
   names → `TruncatedSVD(n_components=48)` → `float32` L2-normalized vectors.
2. **`faiss.IndexFlatIP`** (exact inner product on unit vectors = cosine)
   retrieves **top-8 neighbours per record**, self excluded.
3. Deterministic blocking unions any pair sharing a **website domain** or a
   **city + postal code** combination (blocks larger than 30 records are
   skipped and counted — bounded behaviour on degenerate uploads).
4. Pairs are deduplicated in canonical `(i < j)` order; total candidates are
   bounded at 6,000 per analysis with a descriptive error beyond that.

The retrieval representation is **fitted on training names only** and applied
to validation/test (and, at serving time, to uploaded names). On the current
benchmark, FAISS+blocking covers **100% of same-entity pairs** in both the
validation and test splits (candidate pair recall 1.000/1.000) — measured
separately from classifier quality so retrieval gaps can never hide behind
classifier metrics.

## 4. Pair features (19, fully interpretable)

Computed by the *same* function in training and serving
(`backend/vendorlens/ml/features.py`):

| Group | Features |
|---|---|
| Name similarity | `name_char_similarity` (SequenceMatcher), `name_token_jaccard`, `name_token_containment` |
| Legal suffix | `suffix_both_present_same`, `suffix_both_present_different` |
| City | `city_both_present_equal`, `city_both_present_different`, `city_missing` |
| State | `state_both_present_equal`, `state_both_present_different`, `state_missing` |
| Postal | `postal_both_present_equal`, `postal_both_present_different`, `postal_missing` |
| Website | `website_both_present_equal`, `website_both_present_different`, `website_missing` |
| Address | `address_char_similarity`, `address_missing` |

Missing optional fields produce **missingness indicators**, never a match or
mismatch signal. No ground-truth label, split id, or answer key is accepted by
the feature API (asserted by `tests/test_features.py`).

## 5. Train / validation / test design (no identity leakage)

- **Splits are made by canonical entity, not by record**: 204 train / 44
  validation / 44 test entities (70/15/15). An entity's aliases never appear
  in two splits — enforced by assertion in `split_by_entity`.
- Pairs are generated **within** each split (retrieval runs on the split's own
  records), so no pair crosses split boundaries. Labels are canonical-entity
  equality.
- Each split's pair set = retrieved candidates + sampled random negative pairs
  (≈15% of candidate count) to include easy negatives alongside hard ones.
- The TF-IDF/SVD representation is fitted on **training names only**.

Current split sizes: 596 train / 126 validation / 128 test records; the test
pair set holds 135 positive and 591 negative pairs.

## 6. Baseline vs trained model

- **Baseline** (deterministic rule): predict *match* when normalized-name
  character similarity ≥ **0.85**.
- **Trained model**: `StandardScaler + LogisticRegression(class_weight="balanced",
  max_iter=1000)` over the 19 features. Coefficients remain inspectable;
  `predict_proba` is a model-estimated score, not a guarantee of real-world
  identity.

Both are evaluated on the **same held-out test pairs**.

## 7. Threshold selection (validation only)

Thresholds are chosen on the validation split and frozen before the test split
is scored:

- **decision threshold** = F1-maximizing cut (0.21).
- **likely-match band** = the stricter of the precision ≥ 0.97 threshold and
  the 5th percentile of true-match validation scores (0.93).
- **review lower bound** = the stricter of the recall ≥ 0.98 threshold and the
  95th percentile of true-non-match validation scores (0.02).

Because the classifier's scores are strongly bimodal, a single F1-maximizing
cut would collapse all three recommendation bands onto one point; the
percentile criteria keep a genuine *needs review* band for ambiguous pairs
(e.g. lookalike siblings scoring 0.3–0.9). Bands are review recommendations,
not verified business rules — every band requires a human decision before any
consolidation.

## 8. Measured results (held-out test, seed 42)

| Approach | Precision | Recall | F1 |
|---|---|---|---|
| Baseline rule (sim ≥ 0.85) | 0.9381 | 0.7852 | 0.8548 |
| Trained model | 0.9310 | **1.0000** | **0.9643** |

Confusion matrix (trained model): TP 135 · FP 10 · TN 581 · FN 0
(baseline: TP 106 · FP 7 · TN 584 · FN 29). The trained model recovers the 29
true duplicates the rule misses, at the cost of 3 additional false positives —
an explicit, favorable trade for a review workflow where false negatives stay
hidden while false positives merely cost an analyst look.

The most confident false positive (score 0.865) is
*Unionville Design Products Inc.* vs *Unionville Precision Products LLP* — a
deliberately crafted hard-negative sibling pair. Full difficult-case lists are
in `reports/metrics.json` → `difficult_cases`.

## 9. MLflow experiment tracking

Real runs, local file store (`./mlruns`, git-ignored):

- Experiment `vendorlens-supplier-matching`
- Baseline run `baseline-name-similarity-rule` (run id recorded in metrics.json)
- Model run `logistic-regression` with parameters, all metrics above, the
  serialized `model_bundle.joblib` and `metrics.json` attached as artifacts.

Reproduce with `make train`; inspect with `make mlflow-ui`.

## 10. Serving parity

The API loads `artifacts/model_bundle.joblib` (model + vectorizer + SVD +
feature schema + thresholds + versions) and **applies the training-fitted
representation** to uploaded names — never refitting at serving time — then
computes features with the identical training code path. Fixed inputs and a
fixed bundle produce identical scores (asserted in `tests/test_training.py`).

## 11. Bias, limitations and generalization

- The benchmark encodes *this generator's* corruption patterns. Real registers
  contain OCR noise, transliteration, mergers/acquisitions, shared contact
  details and multinational naming conventions the generator does not model.
- Logistic regression on 19 features cannot capture exotic interactions;
  this is a deliberate transparency/latency trade (see
  [ENGINEERING_DECISIONS.md](ENGINEERING_DECISIONS.md)).
- Recommendation bands were calibrated on validation data of this benchmark;
  deployments with different cost ratios should recalibrate.
- The system never verifies legal identity and never merges automatically —
  it routes evidence to humans.
